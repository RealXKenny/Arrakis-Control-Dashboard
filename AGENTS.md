# Arrakis Control Dashboard

Use this map before searching. Keep it current when structure or core contracts change.

## Runtime

- Stack: Node.js 22+, Next.js 16 Pages Router, React 19, TypeScript, npm, Redis, Vitest, and Playwright.
- Dev: `npm run dev`; defaults to `http://127.0.0.1:2008`, with `SERVER_HOSTNAME` and `SERVER_PORT` configurable in `.env`. Production: `npm run build`, then `npm start` with the same binding variables.
- Standard checks: `npm run format:check`, `npm run typecheck`, `npm run lint`, `npm test`.
- Extra checks: `npm run test:production` for runtime/API changes; `npm run test:browser` for UI behavior.
- `LOG_LEVEL=DEBUG` writes redacted metadata and compact background-poll diagnostics to the colored console only. Successful polling is omitted at `INFO`; warnings and failures remain visible. There are no log files or Sentry.
- Releases: bump the stable SemVer in `package.json` and add the matching `## [X.Y.Z] - YYYY-MM-DD` section to `CHANGELOG.md`; successful `main` CI creates the tag and GitHub Release. The release job also refuses any commit that is not already on `main`. CI shards the browser suite across four runners; `test:production` runs on the first shard.
- Only a new stable version release publishes `ghcr.io/realxkenny/arrakis-control-dashboard:latest`, `v<version>`, and `sha-<commit>` images after successful `main` CI. The importable egg is `pterodactyl/egg-arrakis-control-dashboard.json`; its allocated `SERVER_PORT` comes from Wings.

## Map

- `src/pages/_app.tsx` loads the shared Announcify announcement widget with its public project ID and explicit API origin. `src/proxy.ts` allows the vendor script, API, hosted images, and Google Fonts assets through CSP. It also issues a per-request `'nonce-…'` that `src/pages/_document.tsx` passes to `Head`/`NextScript`, so Next.js's inline Turbopack bootstrap runs without `'unsafe-inline'`; keep pages dynamically rendered.
- `src/modules/marketplace/` owns sanitized base sharing and community listings. Redis stores negative publication timestamps for newest-first order; catalog reads use bounded rank ranges, never positive score bounds. Cards use owner-captured 640 × 360 PNGs, never automatic front detection or WebGL thumbnails. Owner-verified `/api/bases/[baseId]/preview` stores normalized front views and bounded pictures in Redis; saving a picture updates an existing listing without changing its rank. Publication requires a picture; older listings without one retain their layouts but require the owner to capture a picture before marketplace import is offered. Sharing and JSON uploads prompt for a front; capture framing fits all rendered pieces while preserving the selected angle. Marketplace imports normalize optional export fields and use the shared `bases/utils/import-blueprint.ts` delivery path without weakening import validation.

- Marketplace listing responses derive session-specific `editableBaseId` hints from verified owned-base IDs and the original publisher/base hash, including legacy listings. `MarketplaceCard.tsx` offers **Change picture** only for those listings, captures the published layout, and updates the saved picture through the ownership-checked preview endpoint without republishing.

- `src/components/Topbar.tsx` and `topbar.module.css` provide shared pill navigation across public, member, and admin pages. `src/styles/pillbox-theme.css` owns the neutral Tailwind palette and fluid `workspace-frame` gutters; the page shell uses it without a fixed desktop width cap. It also owns the motion layer: `fly-in`, `fly-in-stagger` (staggered children), `view-enter` (a keyed `display: contents` wrapper that replays portal view entrances), `shimmer` loading placeholders and `lift-hover` cards. Never animate an ancestor of the map or full-screen base preview layers, and keep every animation off under `prefers-reduced-motion`. Playwright runs with reduced motion except the motion test in `theme.spec.ts`.

- `src/pages/`: thin Pages Router pages/API entry points. `/` is the public landing page; `next.config.ts` redirects legacy `/home` links there and preserves query strings. `/portal` remains the signed-in workspace. There is no separate public operations dashboard.
- `src/modules/<feature>/`: UI, hooks, normalization, utilities, and server handlers for `auth`, `bases`, `changelog`, `guilds`, `home`, `map`, `player`, and `portal`. Each feature keeps CSS modules in its own `styles/` folder.
- `src/infrastructure/`: Dune Console/adapter and Discord clients, API boundary, cookies, and API cache. Start with `dune.ts`, `dunedocker/transport.ts`, or `pages-api.ts`.
- `src/lib/` is grouped by concern: `redis/` (node-redis `client.ts`, the ioredis pool/cluster + circuit breaker in `pool.ts`, and the optional `data-provider.ts`), `security/` (`session-store.ts`, `rate-limit.ts`, `api-capacity.ts`), `cache/` (`client-cache.ts` for browsers, `read-cache.ts` for the server), and `http/` (bounded `response.ts` and `timeout.ts`). `env.ts` is the canonical environment schema (`src/config/env.ts` re-exports it); `logger.ts`, `errors.ts`, `value.ts`, `types.ts` and `assert-server.ts` stay at the root. `lib/redis/` and `lib/security/` are server-only, which the architecture test enforces.
- `src/config/`: authoritative server environment schema, production validation, and the dev/production server launcher.
- `src/instrumentation.ts`: runtime validation, Console warmup, startup log, and population recorder.
- `src/assets/`: favicon, application images, and compressed Deep Desert terrain bundles. It is large; do not enumerate it unless necessary.
- `src/modules/map/terrain/` is split into `scene/` (lazy Three.js scene: `MapScene3D.tsx` owns camera/disposal, `sceneGeometry.ts` aligns markers with rendered terrain triangles, `sceneModels.ts` bounds model lifecycles), `models/` (building, vehicle, worm and world models, `ueTransform.ts`, and the offline `buildClientModels.mjs`) and `surface/` (measured terrain geometry, materials, shaders and asset loading). The 2D WebGL2/image viewer is the automatic compatibility fallback. Model/terrain assets remain allowlisted and base exports retain ownership checks.
- `src/modules/bases/components/BasePreview.tsx` lazily opens one owned-base renderer using the shared `buildingModels.ts` catalogue. The fast preview uses the simplified `models/native` pack; the detailed preview uses `models/client` (MapViewer3D client LOD0 DML1 meshes, UVH1 UVs, one albedo per mesh, `_Glass` companion accessories), rebuilt offline by `map/terrain/models/buildClientModels.mjs <extracted MapViewer3D-cdn>`. Both share metre-scaled UE X/Z/Y axes and native actor/catalogue transforms; never infer yaw or swap left/right models from template names. `utils/model-export.ts` bounds authorized export requests; preserve native per-item transforms, indexed pentashield sizes, partial coverage reporting, and disposal. `src/modules/portal/components/BaseInventory.tsx` owns the responsive storage dialog and keyboard focus lifecycle.
- `src/modules/guilds/` owns the signed-in Guilds recruitment page (`/portal?view=guild-requirements`) under Community; leader-only settings stay in the My Guild view. Redis stores bounded listing records and a newest-first rank index; publishing/unlisting is atomic. Settings and logo mutations share fresh server-verified linked-player leadership (role 100), matching both pawn and controller IDs; names and cached IDs never authorize edits. Member responses include the session-specific `canEdit` permission used to show Settings and logo controls.
- `src/modules/sharing/`: public Discord component-card JSON and Open Graph/Twitter metadata, rendered before hydration on `/` and `/portal`. Only the canonical `APP_URL` origin enters page props. Keep the payload below 3,000 bytes, link-only buttons, no member data, and the versioned PNG allowlist under `/api/assets/share/`.
- `src/modules/map/utils/markers.ts` distinguishes static template IDs by location and deduplicates samples before legend filtering. Live object keys retain identity during movement and include instance identity. Projection lookups, React keys, model lifecycles, and search results must use the same identity function. `terrain/worldModels.ts` generates spice/wreck/flour-sand models; `sceneModels.ts` allocates only the nearest 40 and disposes them on range/filter/detail changes. Map HUD controls portal into the workspace toolbar; camera projection and terrain rendering stay in the same frame.

- `src/modules/theme/`: local calendar theme matrix, pure resolver, and pre-paint browser controller; `/api/theme-script` serves CSP-compatible JavaScript. Palette styles live in `src/styles/global.css`; `src/styles/pillbox-theme.css` binds the modern UI accent to them. Optional class/message/asset metadata is applied without inserting layout elements.
- `src/modules/bot/server/`: versioned read-only service API for sanitized guild-wide world data; separate `BOT_API_TOKEN` authorization, no browser session impersonation.
- `src/modules/admin/`: Overview control center, Setup/connection diagnostics, complete API reference, grouped administration workspace, typed catalog forms, paginated/filterable result tables and contextual entity actions. `operation-fields.ts` derives controls from documented parameters; Advanced request fields retain complex Console payloads. The 383-operation catalog includes the original reference plus guild membership mutations. Guild oversight inspects bounded recruitment/application data and read-only conversations through `/api/admin/guilds/*`, records inspection metadata, and offers guild leader support chat. `/admin` and `/api/admin/*` revalidate the exact OAuth-verified admin ID, configured guild, role, and session. The admin route has no navigation links on public or member pages. Separate `ADMIN_CONSOLE_API_KEY`; Console browser-only restrictions remain enforced. Upload/download/event streams are bounded; all API entry points still use the common boundary.
- `modules/admin/navigation.ts` maps all catalog groups into six grouped sections and their tabs (Control center, Players & community, Game assets, World & economy, Operations, Configuration & advanced). `/admin?tab=<id>&operation=<id>` is the shareable, history-aware location; `AdminWorkspace` renders `PillNav` rows (shared pill styling in `src/components/PillNav.tsx`, also used by `Topbar`) plus a breadcrumb. `ConsoleOnly.tsx` lists restricted operations as an honest Console handoff. Dedicated screens live in `modules/admin/screens/` (Players, Vehicles, Bases & storage, Maps & worlds, Backups, Market, Server, Logs, Care packages, Admin tools (communications, catalogs, Landsraad goals, message settings, history), Updates, Addons, Guild membership, Discord integrations, Public directory and Live map (map/partition chosen explicitly, layers link to player/base/storage records, teleport requires a partition) so far (Updates, Addons, Discord adapter-write and directory/settings writes are read/check-only; restricted writes render `ConsoleHandoff`, never a form). `isDedicatedKind` in `navigation.ts` derives which tabs have manager screens; Maps is a read-focused dashboard with confirmed balancer/parallelism changes, while map start/stop/mode, memory, autoscaler and UserEngine writes link to the full tool forms because their target/action formats are unverified; URL-driven list/detail/section state via `useAdminUrl`, reads via `useAdminQuery`, mutations only through `ConfirmDialog` with typed phrases from the catalog, `client.ts` attaches the gateway acknowledgement); the generic typed catalog forms remain behind each screen's `Advanced tools` link (`advanced=1`) and are still the only interface for every other group. `tests/unit/app/admin-navigation.test.ts` fails if any operation lacks exactly one screen; the generated report is now a coverage matrix.
- `modules/admin/server/overview.ts` authorizes before reading ten allowlisted Console sources through the existing sanitized gateway, with four workers and six-second per-source deadlines. It returns only normalized metrics, bounded service summaries, connection status/timing and configuration booleans. Missing totals stay unknown rather than counting the sampled page. `useAdminOverview` polls while visible every 30 seconds, retains at most 20 trend readings in memory, and backs off on transport failure. `tests/api/admin-catalog.test.ts` exercises all 383 catalog entries with mocks, including restricted operations and binary/multipart/event transports, and generates `test-results/admin-api-report.md` (never commit it).
- `src/lib/security/api-capacity.ts`: per-worker API admission budget before Redis work. Read-cache overflow returns 503; realtime snapshots coalesce for one second after per-request authorization. `tests/load/dashboard.k6.js` is the optional staging load harness.
- `src/modules/map/server/realtime.ts`: Console snapshots available to all signed-in dashboard members of the configured guild; `hooks/useRealtimeData.ts` polls every two seconds with instance selection. No separate realtime role is required; anonymous player/vehicle objects are excluded.
- `tests/`: API, architecture, unit, browser, helpers, and `smoke-production.mjs`. Unit tests are grouped by area (`unit/lib`, `unit/infrastructure`, `unit/bases`, `unit/map`, `unit/portal`, `unit/app`, `unit/release`); browser specs import `test`/`expect` from `tests/helpers/browser-test.ts`, which disables entrance animation and smooth scrolling for stable measurements.
- Root runtime behavior: `src/proxy.ts` (Middleware renamed in Next.js 16) and `next.config.ts`. `docker-compose.yml` runs the app beside a local Redis for development.
- The Docker image links `.next/cache` into `/home/container/.cache/arrakis-dashboard`. `src/config/server-launcher.mjs` prepares the image cache after the Pterodactyl volume mounts; release checks verify writes as the container user with a read-only image filesystem.
- Guild listing logos stream through the authenticated `/api/guilds/[guildId]/logo?image=1` route. Joining applications use `/application` for the signed-in applicant’s own record and `/applications` for verified leader review. Redis stores at most 200 applications per guild, indexed for bounded 20-row reads, with atomic duplicate prevention and a 90-day inbox expiry refreshed by new submissions. Applicant identity comes from the session and verified linked character; acceptance adds the freshly verified linked character as a Member through Console before saving accepted status. New submissions snapshot the player ID; changed links must reapply. Per-application review leases serialize decisions and generation checks protect reapplications. Already-present members reconcile without another write; Console writes never retry. Every guild mutation checks same-origin requests.
- Guild settings support up to eight unique UUID-keyed required/optional application questions. Submission validates current questions and snapshots their wording; changing questions during submission returns a retryable conflict. Dashboard administrators may inspect application conversations through their separate read-only admin routes, without changing unread receipts. Private application chat reads `/applications/[applicationId]/messages` and sends via its POST-only `/send` child, keeping polling separate from send-rate limits. Only the applicant or freshly verified current leader may access chat. Each conversation keeps at most 100 messages of 1,000 characters, deduplicates recent retried sends, expires with application storage, and is removed with its application. Per-submission conversation IDs isolate reapplications. Browser chat polls every two seconds without overlap while visible, backs off on failure, preserves failed-send drafts, and aborts on close.
- `modules/guilds/server/membership.ts` handles leader-only Console member additions, promotion/demotion, removal, and disbanding. It checks same-origin requests, fresh leadership and roster ranks, explicit destructive confirmations, protects the Leader, sanitizes responses, and never retries writes. UI controls beside member names refresh the roster and permissions after changes; disbanding best-effort clears recruitment records, applications, logos, and chats, reporting cleanup failures without retrying the already-completed Console operation.
- Applications have no fixed applicant fields. Guild owners configure short text, paragraph, dropdown, timezone, checkbox, or decimal-number questions; at least one is needed for new applications. `question-fields.ts` centralizes canonical form versions, supported IANA region zones plus UTC, type/required/choice validation, and answer formatting. Submission snapshots question wording and type. Legacy untyped questions remain paragraphs, and old standard answers remain readable. Dropdown choices are bounded to 30 unique entries; numeric answers stay strings.
- `modules/guilds/server/support.ts` stores private administrator/current-leader conversations (100 messages, 1,000 characters, 90-day TTL, retried-send deduplication) under `arrakis:guild-support:<guildId>`. Leader reads/writes reverify linked-character leadership; admin routes reverify the exact admin session. Leaders reply in My Guild Settings; disband cleanup removes support history. These are in-dashboard messages, not Discord DMs.
- Support unread counts use separate administrator/leader receipts in a two-field Redis hash beside each support thread. Exact displayed opposite-party message IDs are acknowledged through POST `/support/read` or admin `/messages/read`; merely loading status never marks read. `support-receipts.ts` maintains an expiry-scored unread-reply index for the global admin badge, removes evicted/disbanded messages, and bounds per-guild scans to 100 messages. `useSupportUnread` polls counts while visible, aborts on close, backs off, and refreshes after acknowledgement events. My Guild/Settings and admin navigation, oversight, guild cards and leader-chat controls show counts.
- Applicant card status uses the session-scoped, bounded `/api/guilds/application-status` batch endpoint. Applicant-only POST `/messages/read` receipts record exact reviewer message IDs per conversation in Redis, expire with application storage, and clear only visible chat messages. Card badges poll while visible; opening status never marks chat read.
- Guild directory presentation uses `GuildListingCard.tsx` and `styles/listings.module.css`: responsive cards with bounded previews, explicit details expansion, saved logos or monograms, and real question counts. Expanding details or an application spans the card across the grid; the application inbox keeps its separate styles.

## Contracts

- API entry points delegate to feature handlers through `runPagesApiHandler`. The read-only binary route `src/pages/api/assets/[...path].ts` is the only intentional exception.
- Browser code must not transitively import infrastructure, `src/config/env.ts`, `server` directories, or server-only Redis/session/rate-limit/logger modules. Architecture tests enforce this.
- Normalize external payloads from `unknown`; never expose raw errors, credentials, admin payloads, or unbounded data. Keep unsafe-size numbers as decimal strings until display.
- Redis is the only persistent store and backs production sessions/rate limits. Do not add PostgreSQL or another database.
- Sign-in: `AUTH_PROVIDER=discord` (default) uses the direct Discord OAuth callback; `AUTH_PROVIDER=clerk` (with `CLERK_SECRET_KEY` and `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY`) runs `clerkMiddleware` in `src/proxy.ts`, shows `/sign-in`, and bridges through `/auth/complete` (`modules/auth/server/clerk-complete.ts`). Both paths end in `establishDashboardSession`, which re-verifies the guild role with the Discord token and issues the Redis session keyed to the Discord user ID; never trust a Clerk user ID for ownership or admin checks. CSP adds only the Clerk Frontend API host decoded from the publishable key, `img.clerk.com`, and Cloudflare Turnstile.
- Dune Console uses `Authorization: Bearer <CONSOLE_API_KEY>`. Do not restore password login, session cookies, CSRF, or automatic reauthentication.
- `ADAPTER_TOKEN` is distinct from `CONSOLE_API_KEY`; never interchange or merge these credentials.
- `/items/*`, `/maps/*`, and `/favicon.ico` rewrite to the hardened asset route backed by `src/assets/`; terrain bundles use `/api/assets/terrain/*` directly. Do not recreate `public/`.
- Deep Desert terrain uses Console `coriolisLayout` values 0-11 and portable RGBA textures. Keep terrain paths allowlisted and preserve the image fallback when WebGL2 is unavailable.
- Preserve sanitized request IDs, method checks, private/no-store and security headers, same-origin mutation checks, POST-only logout, ownership checks, bounded provider responses/retries/timeouts, verified Discord guild-role authorization, host-prefixed production cookies, and recursive secret redaction. Operational provider errors omit stacks.

## Environment

- `.env` is ignored and secret; `.env.example` is the only committed template. Never print values or create `NEXT_PUBLIC_` secrets.
- `APP_URL` is the canonical public origin; the Discord callback is derived as `<APP_URL>/auth/callback`. Do not add a separate redirect URI variable.
- Empty environment values normalize to absent values. Add or change variables in `src/lib/env.ts`, `.env.example`, tests, and README together.
- Builds work without deployment secrets; production runtime does not.

## Change discipline

- Before changing Next.js behavior, read the local guide required above. Never edit the managed block.
- Prefer feature-module changes and keep page entry points thin. Add the smallest focused regression test.
- Keep `Dev note:` easter eggs inside executable code near real logic, never in file headers or non-code files. Sprinkle them selectively, allow multiple in complex files when each fits its nearby code path, and mix corny dad jokes with developer and Dune humor.
- For runtime, routing, environment, or infrastructure changes, run standard checks plus build and production smoke.
- Keep `package.json` and `package-lock.json` versions synchronized when bumping a release.
- Never commit generated `.next/`, `coverage/`, `test-results/`, `playwright-report/`, or `tsconfig.tsbuildinfo` output.
- Do not recreate removed `docs/`, `scripts/`, `public/`, debug-output folders, Sentry files, PostgreSQL configuration, or `CLAUDE.md`.
- Preserve unrelated user changes. Do not perform broad cleanup outside the requested scope.
