# Notification preferences (N093)

Open **Notifications → Actionable inbox → Notification preferences**. Preferences apply to the inbox's Assets, Supply, Market, Operations, Events, Maintenance and Assistance categories, including urgent alerts. They do not change existing chat/support notifications, sound settings, game state or source permissions. Unsupported market/stockpile/generator monitoring remains unsupported; a preference does not enable those engines. Existing records without newer feature fields receive enabled, zero-cooldown defaults when read.

## Controls

- Enable or disable each category independently. All categories default on.
- Configure each category's cooldown from zero through 10,080 whole minutes (seven days). Zero is the default and disables cooldowns. **Reviewed** starts a cooldown for that specific alert; it does not pause unrelated alerts in the category or mark game work complete.
- Enable quiet hours using start/end local times and a saved IANA timezone, such as `America/New_York`. Defaults are disabled, 22:00–07:00, UTC. **Use device timezone** fills the timezone field; it is saved only with the form. Overnight windows work across midnight. Start is inclusive, end exclusive. Enabled windows require different start/end times. Daylight-saving skipped/repeated hours follow the selected timezone's local clock.
- **Dismiss** hides the current alert version. A changed title, detail, priority or destination changes its content fingerprint and may bring it back. **Snooze** pauses the alert identifier for 15 minutes, one hour, eight hours or 24 hours, even if the reading changes.
- **Show muted alerts** reveals currently authorized suppressed alerts and their reasons. **Restore alert** removes that alert's dismissal, snooze and review timestamp. Category and quiet-hour rules still apply.
- Form edits are drafts until **Save notification preferences**. **Discard preference changes** restores the last confirmed configuration. **Reload saved settings** discards the local draft and checks the current authorized inbox/settings again.

Rules use the server-supplied check/confirmation time. Quiet-hour boundaries, snooze expiry and cooldown expiry take effect on the next inbox check or confirmed settings action; there is no background delivery, polling, catch-up burst or automatic unmuting of stale source snapshots. Refresh after a window ends. Existing hidden-document clearing and fresh guild-source verification remain in force.

Defaults preserve N092's behavior. Muting is presentation policy, never authorization: source reads still require existing session/character/guild checks, and current authorized summaries are returned even when muted. This feature sends no push notifications, email, Discord messages or sounds.

## Persistence, privacy and concurrency

Redis stores one versioned record at `arrakis:notifications:v1:<SHA-256(account ID)>`. It contains a UUID revision, configuration and at most 120 recently touched alert controls. Controls store opaque per-account alert IDs, content fingerprints and server-generated dismissal/review/snooze metadata. Alert text, source records, coordinates, guild rosters and inventory snapshots are not persisted. Adding a 121st distinct control evicts the oldest touched control; an evicted dismissal may appear again. Restoring leaves a revision so stale tabs cannot recreate removed controls.

The stored record is bounded to 64 KiB, with 90-day inactivity retention refreshed on read/write. Each read and atomic compare-and-set uses one Redis key, compatible with standalone and Cluster without multi-slot operations or database-selection commands. Concurrent first saves and config/action races have one winner. Corrupt, oversized, wrong-type or unavailable storage fails closed instead of silently replacing preferences with defaults. No automatic mutation retry occurs. An uncertain/timed-out save requires explicit reload before another attempt. Snooze/review timestamps are generated by the server; callers cannot submit deadlines.

## API

`GET /api/v2/inbox/preferences` returns `{ record, checkedAt }`. A missing record returns validated defaults with a null revision. `GET /api/v2/inbox` includes the same envelope in `notifications` alongside `data`. A preference read failure prevents loading/rendering an inbox that ignores stored controls.

`POST /api/v2/inbox/preferences` accepts one strict action:

| Action      | Fields beyond `action`                                                                   |
| ----------- | ---------------------------------------------------------------------------------------- |
| `configure` | `revision`, `config` (schema version 1, all seven feature settings, quiet-hour settings) |
| `dismiss`   | `revision`, opaque 64-character hex `id`, 64-character hex content `fingerprint`         |
| `snooze`    | `revision`, `id`, `minutes` (15, 60, 480 or 1440)                                        |
| `review`    | `revision`, `id`                                                                         |
| `restore`   | `revision`, `id`                                                                         |

Responses return the confirmed record and server check time. Subsequent writes must carry its UUID revision. Stale revisions return 409; drafts remain visible. Request bounds are 8 KiB. Unknown fields, ownership claims, timestamps, invalid zones and out-of-range values are rejected. Both endpoints derive ownership only from the verified session, do not require a game guild or character link, return no-store JSON and share a 30-request/account/minute budget that fails closed. Mutations require same-origin JSON requests. Invalid or invented opaque IDs can affect only the caller's bounded private controls, never another account or source eligibility.

## Operations and verification

No dependency, environment setting or explicit migration is required: records initialize lazily. Deployment rollback can stop reading these keys without touching source/progression data; retention eventually removes inactive preferences. Do not delete production records to reset a test. Schema version 1 rejects unknown versions rather than guessing their meaning.

Run standard checks, production build/smoke and the browser suite. Focused tests live in `tests/unit/inbox/preferences.test.ts`, `tests/api/notification-preferences.test.ts`, `tests/browser/notification-preferences.spec.ts` and `tests/integration/redis-notification-preferences.test.ts`. Real disposable standalone/Cluster integration covers account isolation, retention, concurrent first writes/config/action races, server timestamps, restore revisions, 120-control bounds and corrupt/wrong-type/oversized storage. Never configure integration targets against production; the test harness flushes its target.

Browser coverage includes persistent dismiss/snooze/review/restore, category and timezone quiet-hour controls, urgent muting, cross-account privacy, stale-tab conflicts, failed saves, touch-enabled workflows, five viewport widths from 320 to 1440px and WCAG AA automation with the editor open. Native Safari, physical devices and screen-reader products remain unverified.
