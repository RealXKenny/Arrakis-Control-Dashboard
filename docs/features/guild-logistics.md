# Guild operations and logistics

Roadmap items N061–N070 extend the private [operations planner](guilds.md#operations-planner) and add a **My guild → Logistics** tab (`/guild?tab=logistics`). Every read and write re-verifies the caller's linked character against the fresh guild roster. Leader-only actions need a fresh role-100 check. Everything here is a planning record. Nothing moves items, vehicles, currency or characters in game, and nothing is sent to Discord.

## Inside each operation

| Item | What members see                                                                                                                                                                                                                                                                                                                                                                                                             |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| N063 | **Waitlists.** When a role is full, members can join that role's waitlist (50 entries per operation). When a seat frees up, the earliest waiter for that role gets an explicit invitation that holds the seat for two hours, or until the start if that is sooner. Nobody is signed up until they accept. Declined or lapsed offers pass to the next waiter. Offers lapse when the run starts.                               |
| N064 | **Readiness cards.** Signed-up members can share a status (ready, partly ready, not ready), tick the operation's preparation items and add a short kit note. Cards are labelled self-reported and are never checked in game. Members can stop sharing at any time. Removing a preparation item clears its ticks.                                                                                                             |
| N066 | **Convoy plan.** Leaders assign vehicles (from the guild fleet or entered by name), crews drawn from current sign-ups, cargo loads with whole-number quantities, and destinations linked to the operation's waypoints. Each crew member and fleet vehicle appears once. Removing a sign-up removes them from the crew. Item weights are not reported, so the plan never claims a load fits.                                  |
| N067 | **Role briefings.** Leaders write one briefing for each enabled role (pilot, scout, escort, harvester, support and supplier). The server sends each member only the briefing for the role they hold or are invited to. Leaders see all of them.                                                                                                                                                                              |
| N068 | **Waypoints and rally points.** Up to 12 private points, each with a purpose, a map (Hagga Basin or Deep Desert), an optional sector (A1–I9) and optional world X/Y. The X/Y values are copied from a marker's location details on the live map. **Show on map** opens the existing map in 2D with a target ring and the label in the status bar. The pin lives only in the member's own URL, and the map does not store it. |
| N069 | **After-action reports.** Once an operation is completed, cancelled or past its end, leaders record the outcome, a summary and up to 10 lessons. Participants and leaders can add up to three screenshots (PNG, JPEG or WebP up to 700 KiB, re-encoded to bounded WebP and served only to current members). They can also propose follow-up tasks (20 per report). Leaders accept, decline or mark accepted tasks done.      |

## Logistics tab

| Item | Description                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| N061 | **Operation templates.** Up to 20 templates per guild reuse roles, meeting point, details, duration, preparation list, briefings, waypoints and notes. They can optionally repeat weekly or every two weeks at a weekday and time in a named IANA timezone. **New from template** in the planner fills the editor with the next suggested start, which accounts for daylight-saving changes. A leader still reviews and saves each operation, and nothing is scheduled automatically. **Save as template** captures an existing operation.                                                |
| N062 | **Availability board.** Each member shares up to 14 weekly windows in their own timezone. Windows may cross midnight. The board converts every window to the viewer's timezone for the next seven days and counts a member only for hours a window fully covers. It also suggests the best start times for runs of one to four hours. Entries of members no longer on the roster are hidden. Entries older than 30 days are flagged as possibly outdated.                                                                                                                                 |
| N065 | **Fleet dispatch.** Members publish vehicles their linked character owns. Ownership is checked against the Console at publication and on **Refresh readings**. The condition, fuel and storage readings shown are from that check, with their timestamp. The owner or a leader books a vehicle for up to 48 hours, starting within 60 days, with a roster pilot and an optional linked operation. Overlapping bookings for the same vehicle or pilot are refused. The booker, pilot, owner or a leader can cancel. Owners and leaders can withdraw a vehicle, which cancels its bookings. |
| N070 | **Landsraad campaign.** The current term's objectives come from the Console's Landsraad read (cached for 60 seconds). Only objectives with a stable ID can be linked, and only reported completion and winning faction are shown. Progress counts are never estimated. Leaders create up to 30 targets, linked to a current objective or guild-defined. Each target has a goal, priority, status and up to 10 assignees. Members can take or leave open targets themselves. Unsupported or unavailable Landsraad data is shown explicitly, and guild-defined targets keep working.        |

## Privacy and identity

Views never include Console player IDs, vehicle IDs or owner IDs. Pilots and assignees are chosen through opaque per-guild member references derived on the server from the fresh roster. A reference to someone who has left the roster is rejected. Sign-ups, waiters, invitations, readiness, uploads and claims are always bound to the caller's freshly verified character, never to a client-supplied ID.

## Storage and limits

- Operation extensions live in the existing operation record: 64 KiB per operation, UUID compare-and-set and the existing retention. Screenshots live in one per-guild hash (`operation-screenshots`) and are written in the same Lua script as their record. Deleting an operation removes its screenshots.
- Templates, availability, fleet and the Landsraad campaign are each one bounded JSON document per guild (`logistics:<section>`): 256, 256, 128 and 64 KiB respectively. They use UUID compare-and-set and 90-day retention refreshed by changes. Corrupt or oversized documents fail closed instead of resetting.
- Changes scoped to the caller's own entry (availability, taking or leaving a target) are re-applied to a fresh document after a revision conflict, up to three attempts. Every other write needs an explicit refresh, and no write is retried automatically.
- All keys share the `{guilds}` hash tag, so scripts are Cluster-safe. Dashboard disbanding removes every logistics key.
- Logistics requests are rate limited per account: 60 reads and 30 writes a minute. Request bodies are capped at 32 KiB.

## API

| Route                                                                                  | Methods   | Notes                                                                                                                                                                                                     |
| -------------------------------------------------------------------------------------- | --------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/api/v2/guilds/[guildId]/operations`                                                  | GET, POST | Adds the `waitlist-join`, `waitlist-leave`, `invitation`, `readiness`, `convoy`, `report`, `follow-up`, `follow-up-review` and `screenshot-remove` actions. Reads persist lapsed or new seat offers once. |
| `/api/v2/guilds/[guildId]/operations/[operationId]/screenshots`                        | POST      | Multipart `revision`, `caption`, `image`. Same-origin only.                                                                                                                                               |
| `/api/v2/guilds/[guildId]/operations/[operationId]/screenshots/[id]`                   | GET       | WebP, `private, no-store`, `default-src 'none'; sandbox`.                                                                                                                                                 |
| `/api/v2/guilds/[guildId]/logistics?section=templates\|availability\|fleet\|landsraad` | GET       | `&candidates=1` on `fleet` lists the caller's own owned vehicles for publishing.                                                                                                                          |
| `/api/v2/guilds/[guildId]/logistics`                                                   | POST      | `{ "section": …, "input": { "action": … } }`, same-origin only.                                                                                                                                           |

## Still needs live verification

Checked locally with unit, API and real-Redis tests. Before relying on these tools in production, check the following on the live server:

- The Console's real Landsraad task fields. Linking needs a `task_id`, `taskId` or `id` on each task; tasks without one are counted as unidentified.
- Vehicle ownership relations from `/api/players/<id>/vehicles`.
- Map pins against calibrated in-game positions.
